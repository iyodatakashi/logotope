# Conventions（作業・コード・ドメインの恒久ルール）

このプロジェクトで Claude が守る作業規約・コード規約・ドメイン方針。過去に個別セッションで指摘・合意された内容を集約したもの。CLAUDE.md の Development Rules と併せて常に適用する。

## 進め方・コミュニケーション

- **結論を一発で正しいスコープで出す。** 依頼は素直に最大スコープで解釈し、開いているファイル・関連 spec に引っ張られてスコープを勝手に狭めない。間違えたら短く直すだけで、長い経緯説明・弁明をしない。各回答末尾の「やりますか？測りますか？」という定型の聞き返しを繰り返さない（必要なら一度だけ）。
- **説明は聞く側の言葉で。** 自作の造語や、まだ存在しない実装上の名前（ファイル名・関数名・ステップ名）を、相手が当然わかる前提で並べない。まず平易な日本語で筋を通し、固有名詞は使う前に一言で定義する。「自分の頭の中の垂れ流し」は説明ではない。
- **バグ修正は原因確定・方針承認の後に着手する。** 未確定・推測のままコードを直さない。手順: ①ログ・エラー code/message・再現条件で原因を特定（推測なら「推測」と明示）②修正方針を提示して承認を得る ③承認後に実装。診断のための読み取り（Read/grep/ログ）は先行してよい。
- **別件を「スコープ外」と切る前に、関係あるか特定する。** 気づいた別件は「今の変更が原因か／今の課題に接続するか」をまず具体的に判定し、無関係と判定できてから外す。判定を飛ばして「別タスクなので」と逃がさない。
- **関連する変更は一度にまとめて実施する。** 影響範囲を自分で判断し、細切れに何往復も確認しない。
- **コミットは `/commit` が呼ばれたときだけ。** コミットの実行・提案・「コミットしますか？」という確認も一切しない。
- **仕組みの有効性を検証するときは変数を1つに絞る。** 本命の効果を相殺・隠蔽しうる補助施策を同時に投入しない。まず本命単体を観測し、その結果を見て補助の要否を別途判断する（spec のタスク計画で補助施策を意図的に延期し、tasks.md に延期理由を明記）。
- **仕様変更に計測・デグレ検証・トグルを毎回付けない。** ユーザーはこれらを過剰と考える。付けるかは明示指示があるときだけ。

## コード全般

- **アロー関数を標準とする。** 理由がない限り `function foo(){}` でなく `const foo = () => {}`。例外は class メソッド等アロー不可の文脈のみ。
- **省略変数名・抽象的すぎる名前を使わない。** `def` のような名前は禁止。ループ/map のコールバック引数や一時変数も含め、役割が分かる名前を付ける。
- **関数はトップダウン順に並べる。** 呼び出し側（高レベル）を上、被呼び出しヘルパー（詳細）を下。ボトムアップにしない。
- **過度な共通化・中央ディスパッチャを作らない。** 画面の操作（アクション・遷移）はその画面コンポーネントに直接書く。key で分岐する中央ディスパッチャ、`models/` への UI オーケストレーション配置、将来分岐しうる UI の共通コンポーネント化を避ける。共通化してよいのは「画面に依存しない真に共通な処理」を `utils/`・store メソッドにまとめる場合のみ。判断基準は「この共通物を変えると意図しない他画面に影響するか？」。（`.kiro/steering/structure.md` にも明文化）
- **使い捨てスクリプトを書かない。** → CLAUDE.md「Development Rules」に本則。要点: 生成・検証・一過性処理も、リポジトリにファイルとして保存すれば OK。私的メモリに保存して済ませない。

## フロントエンド（Svelte / SvelteKit）

- **UI は `@14ch/svelte-ui` を標準ライブラリとして使う。** カスタム実装の前に必ず該当コンポーネントの有無を確認する。design/tasks にも使用を明記。
- **Svelte/SvelteKit の仕様は svelte MCP で裏取りしてから設計・実装する。** runes・$effect・$state・$derived・ライフサイクル・エラーの意味などを記憶で判断しない（`mcp__svelte__list-sections` → `get-documentation`、修正後は `svelte-autofixer`）。
- **コンポーネントにスタイル値を書かない。** color・font-size・line-height・margin・padding・gap など装飾/余白/寸法の値を一切書かない（トークンで正当化して書き足すのも不可）。Claude の担当は「マークアップ＋意味の通った CSS セレクタ（BEM 構造）」まで。値はユーザーが決める。迷ったら足さず、セレクタだけ用意して委ねる。デザイン判断（サイズ・余白・配色・見た目のバリエーション）を自分の判断で持ち込まない。
- **`+page.svelte` / `+layout.svelte` は最小ラッパーにする。** 対応する feature コンポーネント（`src/lib/features/**/XxxPage.svelte` 等）を1つ import して差し込むだけ。例外（+layout にコード可）は ①store のライフサイクル（$effect で start/stop を階層に束ねる）②配下全ページ常時表示のナビ等 ③到達ガード/リダイレクト、のみ。（`.kiro/steering/structure.md` にも明文化）
- **単一用途でドメイン密着（currentTopic 等）の表示コンポーネントは、prop ドリリングより各自 store 直読みを好む。** 逆引き Map 等の派生はデータの持ち主の store にメソッド/getter で集約（例 `personasStore.getAwarenessesByTurn`）。「表示コンポーネントは props を受けるべき」を、その価値が現場に実在するか確認せず持ち出さない。実コスト（テストが vi.mock 化・段階移行中の一時不整合）は正直に併記する。
- **可変配列の index を外部参照・選択キー・対応づけキーに使わない。** 永続要素には最初から安定 id を与え、それを唯一の突合キーにする。複数機能が同じ実体を参照するときは同一性キーを先に1つ決めてから機能を載せる。回避策（再シード・整合合わせ）を書き始めたら、その手前のモデル選択を疑う。「既存パターンに合わせる」も悪い前提まで引き継がない。
- **Firestore 自動保存 ↔ onSnapshot 同期の「編集巻き戻り」を過剰に指摘しない。** 「フィールド blur→setDoc 自動保存」と「onSnapshot で store が変わるたびに編集ドラフトを作り直す $effect」の組み合わせは、latency compensation（hasPendingWrites の即時発火）で単独編集なら実害が出ない。race として第一級の指摘に上げない（実害は多人数同時編集のときだけ。指摘するなら確率・優先度を正しく添える）。

## ドメイン用語・プロダクト方針

- **発言の「指名」は `target` と呼ぶ（`targetPersonaId` / `targetedBy`）。** `nominate` は使わない（変数名・コメント・会話すべてで）。
- **ファクトチェックでは「主張(claim)」と「指摘(finding)」を正確に区別する。** claim＝発言(DebateTurn)内の「〜である」断片（検証対象・入力・削除されない）。finding＝ファクトチェックが出す出力（誤り箇所・正しい事実・理由・出典）。抑制/リラベルの議論では対象が claim か finding かを明示する。
- **討論コンテンツで対立を煽らない。** 「意見が割れる」「対立」「激突」「勝敗」の枠組みで論点や価値を語らない。プロダクトの価値は対立の激しさでなく「複数の立場が筋道立てて成立しうる」こと。多様性は「立場が成立する」で表現する。
- **討論の chapter / agendaItem は必要最小限に集約する。** 数値上限（「3〜4グループ」「N 件まで」等）で機械的に縛らない（価値観がズレる）。代わりに「なぜ集約が要るか」の趣旨をプロンプトで理解させる（章は本質的な問いを一続きでやりきる単位／細かく割ると討論で同じ話が蒸し返され読み手が筋を追えない）。増加を許す文言（「件数は問わない」等）を入れない。
- **再生成（やり直し）は旧データを処理開始時＝生成 API 呼び出しの前に即時削除する。** 主目的は UX フィードバック（押した瞬間に旧データが消え、指示受理が直感的に伝わる）。データ整合性は副次。表示は store が onSnapshot で Firestore をそのまま映すだけなので、即クリアの唯一の手段は Firestore を開始時に消すこと。初回で親 doc 未作成なら `setDoc(merge)` を使う。

## Firebase

- **Firebase Functions の CORS エラーは別原因（404 / 500 / 未ビルド等）を示すことが多い。** Functions がエラーレスポンスを返すとき CORS ヘッダーが載らずブラウザが「CORS エラー」と報告する。`cors: true` を足す前に、ビルド状態・エラーログ・エンドポイント存在を先に確認する。
