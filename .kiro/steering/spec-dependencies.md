# 仕様間の依存の扱い

ある spec が別の spec の成果に依存するとき、依存元の結論を**引き継ぐ**。再導出しない。

## 依存元の `validation/` は必読

`.kiro/specs/{feature}/validation/` は、その仕様が**何をどう作るかを確定して次に引き渡すための
文書**である。実装ファイルやコードのコメントより優先する。

- 依存する spec がある場合、`research` フェーズで依存元の `validation/` 配下を**全て読む**。
  実装ファイル（`*.ts` / `*.py`）だけを見て手法を判断しない。
- コードと文書が食い違う場合、**後から書かれた検証文書が正**。コードは途中状態のことがある。
- **文書と、依存元が実際に生成した成果物が食い違う場合、成果物が正。** 文書は経路の途中で
  書かれたものが残っていることがある。実物を見られるなら見る。

### `validation/` は結論を1本に畳んで残す

**経路ごとに文書を並べない。** 検証の途中で破棄した経路の記録を、確定した結論と同じ場所に
同じ体裁で置くと、読み手はどれが正か文書からは判断できない。

- 残すのは**最終結論1本**。破棄した経路は「採用しない経路」としてその1本の中に畳み、
  なぜ破棄したか・その経路の失敗記録を採用経路の評価に使ってはならないことまで書く。
- 途中経過が要るなら git 履歴に残す。`validation/` には置かない。

**過去の失敗**: `persona-avatar-image-generation` の `validation/` に、採用した経路
（per-persona 編集ベース）と破棄した経路（オフライン量産）の検証結果が3本並んでいた。
結果、`persona-avatar-generation` で**2度の取り違えが起きた**。

1. 実装時: 破棄した経路の道具（`prompt-builder.ts` の `REFERENCE_IMAGES: []`）を根拠に
   text-only 生成を採用。本番の生成物の 17% が受け入れ基準を外れ、フィジビリ1周分が無駄になった。
2. レビュー時: 破棄した経路の失敗記録（「男性 0/1 不合格」）を採用経路の品質評価として引用し、
   成立している手法を「品質未実証」と誤って報告した。

## フィジビリの成果物は「実行できるコード」で残す

散文と画像の山だけを残すと、**採用実装が一意に決まらない**。決まらないものは移植できない。

- 最終手法は**実行可能なコード1本**として残す。プロンプト・定数・入力アセットの作り方を含む。
- 効いているパラメータを**成果物のピクセルの中だけに存在させない**。数値はコードに書き、
  どこから測ったか・なぜその値かをコメントに残す。
- 入力（シード）と出力（生成結果）を**同じディレクトリに置かない**。どちらか分からなくなる。
- 検証用の実装と本番の実装を分けない。分けた時点で、検証で通ったものが本番で同じ結果を出す保証が消える。

**過去の失敗**: `persona-avatar-image-generation` は最終手法の実行コードを残さず、生成物 54 個を
入力・出力・失敗作の区別なく1ディレクトリへ平置きした。スケール一貫の要である
「被写体を正方キャンバスに縦占有 0.855・下余白 0.063 で配置する」という正規化は、
**ベース画像のピクセルにしか存在しなかった**。後続の実装者はこれを復元できず、
人間が「サイズ調整をしていたはず」と記憶していたことで初めて発見された。

## design は依存を取り込む。black box にしない

「この手法は依存元が所有する。本仕様は利用する」と Non-Goals に書くだけで済ませない。
**利用する中身を design の Components / Interfaces に落とす。**

- 落とすべきもの: 使う入力アセット、その選択規則、固定するパラメータ、可変にするパラメータ、
  合否判定のゲート。
- design に無いものは、実装時に実装者が発明する。**設計の空白は必ず埋められる。誤った内容で。**

## 受け入れ基準は依存元のものを使う

生成物・成果物の合否判定に、**実装者が実装後に定義した基準を使わない**。自分の実装が制御している
項目だけが評価軸になり、制御していない項目は失敗として現れない（自己参照の検証になる）。

- 依存元に受け入れチェックリストがあるなら、**それで判定する**。
- 自動判定できない項目は「自動判定できない」と明記し、人手の確認と回収経路（再生成など）を
  設計に位置づける。曖昧にして自動ゲートで担保したことにしない。

## 試験・検証タスクの意味

`spec-impl` の「試験生成」「疎通確認」等のタスクは、**依存元の手法を引き継いだうえで差分だけを
確認する**作業である。ゼロから独自に作り直して「確認した」としない。差分とは、モデル ID の変更・
ランタイムの違い・環境の違いなどを指す。
