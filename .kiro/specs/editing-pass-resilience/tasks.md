# Implementation Plan

> 前提: 編集側（Phase 6）のみ変更し討論側は不変。命名・保存の刷新は再生成で満たすためデータ移行なし。functions 変更は本番デプロイが必要（別作業・タスク外）。

- [x] 1. 基盤: 記事の統合保存（editorial ドキュメント）
- [x] 1.1 導入・締め・所感を1つにまとめた保存先の読み取りと部分上書きを実装する
  - 導入・締め・所感を1ドキュメントにまとめて保存し、所感は参加者ごとにキー分けする（原本 draft と編集後 final を各要素が持つ）
  - 各要素の更新は対象項目だけを書き、他要素を読み書きしない（ドキュメント全体を読み直さない部分上書き）
  - 読み取りは欠落項目を空として補完して返す
  - Observable: 参加者1人分・導入・締めをそれぞれ単独更新しても他要素が変化せず、同時更新でも衝突しないことを単体テストで確認できる
  - _Requirements: 1.2, 6.1, 6.2_
  - _Boundary: editorial-repository_

- [x] 2. (P) 基盤: 生成・編集エージェントの命名整理と導入/締め編集の追加
- [x] 2.1 締め・所感の生成/編集を新名称へ改名する
  - 締めの生成を `outro` 系、所感の生成・編集を `impression` 系へ改名する（中身は不変）。冗長な旧名称を廃止する
  - `comments` は将来の一般ユーザーコメント機能のために使わない
  - Observable: 改名後も既存の呼び出し元から解決でき、型検査が通る
  - _Requirements: 6.3_
  - _Boundary: agents_
- [x] 2.2 導入・締めの編集（整え）処理を新規追加する
  - 導入・締めの原本テキストを、章・所感と同系の editorial 整えで編集後テキストにする処理を追加する
  - Observable: 導入・締めの原本を渡すと整えた編集後テキストが返る
  - _Requirements: 1.2_
  - _Boundary: agents_

- [x] 3. コア: 一括編集を記事へ再配線し堅牢化する
- [x] 3.1 所感の一括生成・編集を統合保存へ書き、参加者単位で堅牢化する
  - 所感の原本生成と編集後を、参加者ごとに統合保存へ部分上書きする
  - 参加者ごとに一時失敗を自動で再試行し、再試行しても駄目な参加者だけを欠けとして残す。他参加者の完成を妨げず、失敗はログに残す
  - Observable: 一部参加者が一時失敗しても他は揃い、再試行後も駄目な参加者のみ欠けた状態で保存される
  - _Requirements: 2.1, 2.2, 2.3, 1.2, 6.1_
  - _Depends: 1.1, 2.1_
- [x] 3.2 導入・締めを「生成→編集」の2工程にして統合保存へ書く
  - 導入・締めを、原本生成に続けて整え（編集）まで通し、統合保存の該当項目へ原本・編集後を部分上書きする
  - 導入・締めの失敗はできる範囲で扱い（編集後を欠けたまま先へ進める）、失敗をログに残す
  - Observable: 導入・締めが原本→編集後で保存され、片方が失敗しても他方と本文の処理は止まらない
  - _Requirements: 2.1, 2.2, 2.3, 1.2_
  - _Depends: 1.1, 2.1, 2.2_
- [x] 3.3 本体(章)の一括編集の堅牢化を統合保存の下で整合させる
  - 章編集の既存挙動（一時失敗の再試行・構造検証不合格は原本フォールバックで failed 記録・後続章を止めない）を維持し、再配線後も完了判定が章の成否から正しく決まることを保つ
  - Observable: 全章が編集済みなら完了、失敗章が残れば停止になる
  - _Requirements: 2.1, 2.2, 1.2_

- [x] 4. コア: 編集のやり直しで全記事を作り直す
  - 編集の開始・やり直しで、記事の全セクション（統合保存と本体の編集後の両方）を破棄してから作り直す
  - 同一の編集実行の中でのステップ再試行では、生成済みの要素を二重生成しない
  - 編集のやり直しが討論の完了状態を後退させない
  - Observable: やり直しで旧記事が破棄され再生成され、実行途中の再試行でも二重生成が起きない
  - _Requirements: 5.1, 5.2, 5.3, 6.4_
  - _Boundary: editing-lifecycle_

- [x] 5. コア: 記事要素の個別再生成
- [x] 5.1 導入・締め・所感の個別再生成を実装する
  - 対象の要素（導入／締め／所感の1人）を、原本生成から編集まで通して作り直し、統合保存の該当項目だけを部分上書きする
  - 対象要素以外を変更しない。失敗時は例外として返す
  - Observable: 指定した要素だけが完成状態になり、他要素は不変
  - _Requirements: 4.2, 4.3, 4.4, 1.2, 6.2_
  - _Depends: 1.1, 2.1, 2.2_
- [x] 5.2 章の個別再生成と編集全体の完了状態の再評価を実装する
  - 指定した章を再編集して保存し、その結果を踏まえて編集全体の完了状態を再評価する（全章が完成に転じたら停止から完了へ更新）
  - 対象章以外を変更しない。失敗時は例外として返す
  - Observable: 失敗していた章の再生成で当該章が完成し、全章完成なら編集全体が完了へ更新される
  - _Requirements: 4.2, 4.3, 4.4, 4.5_
  - _Depends: 2.1_

- [x] 6. 結線: 個別再生成の共通入口（呼び出し口）
  - どの記事要素を作り直すかを受け取り、認証・「編集実行中は受け付けない」拒否・種別ごとのコア処理への振り分け・失敗のエラー化だけを行う薄い呼び出し口を新設する
  - 旧・所感リトライ専用の呼び出し口を撤去し、公開エクスポートを更新する
  - Observable: 編集実行中は受け付けず、確定後は指定要素が再生成される。不正入力・対象不在・再生成失敗はそれぞれエラーになる
  - _Requirements: 4.6, 4.7_
  - _Depends: 5.1, 5.2_

- [x] 7. 結線: 記事表示と個別再生成（FE）
- [x] 7.1 記事の読み取りモデルを実装し購読を統合保存へ集約する
  - 統合保存と本体(章)の編集後を購読し、順序付きセクション（導入→本体→締め→所感）として組み立てる。各要素の状態を「完成／原本のみ／欠落」に導出する
  - 編集後・原本のいずれかがある要素は一覧から消さない
  - Observable: 記事が導入→本体→締め→所感の順で表示され、各要素の状態が判別できる
  - _Requirements: 1.1, 1.3, 1.4, 6.6_
- [x] 7.2 未完成要素の可視化と個別再生成ボタンを実装する
  - 編集が確定した状態（完了または停止）のときだけ、完成していない要素を明示し、その要素の個別再生成操作を提供する（実行中・未実行では明示しない）
  - 再生成の実行導線を追加し、処理中は当該要素の操作を無効化して重複実行を防ぐ
  - Observable: 確定後に未完成要素へ再生成ボタンが出て、押すと当該要素だけが完成表示に更新され、処理中は再押下できない
  - _Requirements: 3.1, 3.2, 3.3, 4.1, 4.6, 4.8_
  - _Depends: 6, 7.1_

- [x] 8. 検証: テスト
- [x] 8.1 (P) バックエンド単体テストを追加する
  - 統合保存の部分上書き（対象のみ更新・他不変）、個別再生成コア（導入/締め/所感/章＋完了再評価）、所感の参加者単位の再試行、共通入口の実行中拒否と振り分けを検証する
  - Observable: 上記が緑になる
  - _Requirements: 2.1, 2.2, 2.3, 4.2, 4.3, 4.4, 4.5, 4.7, 6.2_
  - _Boundary: functions tests_
- [x] 8.2 (P) 統合テストを追加する
  - 一括編集の通しで全要素が編集後まで揃い完了すること、未完成が残った状態から各要素を個別再生成して完成し他要素が不変なこと、やり直しで全記事が破棄→再構築され実行途中の再試行で二重生成しないことを検証する。討論生データ・完了確定が不変であることも確認する
  - Observable: 上記シナリオが緑になる
  - _Requirements: 1.2, 3.1, 5.1, 5.2, 5.3, 6.5_
  - _Boundary: functions integration tests_
- [x] 8.3 (P) FE の型・表示確認を行う
  - 型検査を通し、記事の順序表示、未完成明示が確定後のみ出ること、再生成ボタンの無効化/再有効化を確認する
  - Observable: 型検査が通り、上記表示が確認できる
  - _Requirements: 1.1, 1.3, 3.1, 3.2, 3.3, 4.1, 4.8_
  - _Boundary: FE_

## 並行実行メモ
- Task 1（統合保存）と Task 2（エージェント命名・導入/締め編集）は別ファイル・無依存で並行可（2 に (P)）。
- Task 3・4・5 は基盤（1・2）完了後に着手。3 の各サブタスクは同一チェーンを触るため順次。
- Task 8 の 8.1/8.2/8.3 は別テスト領域で並行可。
- デプロイ注意（[project-no-emulator]）: 命名・保存の刷新と編集側の全変更は同一デプロイに含める（旧コレクションは再生成で孤児化。片方のみのデプロイは表示欠落を招く）。
