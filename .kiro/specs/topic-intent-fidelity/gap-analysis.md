# Gap Analysis: topic-intent-fidelity

## 1. 現状調査（Current State）

### テーマの意図（TopicContext）の供給と消費

供給側は既に一本化されている。`pipeline/topics/topic-context.ts` の `getTopicContext` が唯一の BE 権威経路で、`description` / `sourceContents` / `factBase` を**全段へ同一値で**返す。配線も済んでいる — `persona-chain.ts:61-62, 86-87` は両段へ `topicContext` を渡している。

問題は**消費側**にある。各段が受け取った `TopicContext` のどこを読むかは、段ごとにばらばらの private 関数が決めている。

| 段 | 消費関数 | description | sourceContents | factBase | 見出しと重み |
|---|---|---|---|---|---|
| 事実リサーチ | `fact-research-agent.ts:30,67`（title+description を直接受け取る） | ✅ | — | — | 【この討論で掘り下げたい論点・観点】 |
| **ステークホルダー生成** | `stakeholder-agent.ts:31` | ❌ | ❌ | ✅ | 事実節のみ |
| **ペルソナ生成** | `persona-generator-agent.ts:76` | ❌ | ❌ | ✅ | 事実節のみ |
| 取材 | `interview-agent.ts:315` `buildTopicContextSection` | ✅ | ✅ | ✅ | 【テーマの詳細説明】 |
| 論点・章立て（5段すべて） | `chapter-agent.ts:13` `buildTopicContextSection` | ✅ | ✅ | ✅ | 【テーマの方向性（**最優先**）】＋「方向性から外れた切り口は避けてください」 |
| 導入・締め | `intro-outro-agent.ts:98` `formatTopicContextSection` | ✅ | ✅ | ✅ | 【テーマの詳細説明】 |

- 共有されているのは `utils/prompt-formatters.ts` の `formatFactBaseSection` だけ。description / sourceContents の整形は **3箇所に別実装**（`chapter-agent` / `interview-agent` / `intro-outro-agent`）があり、見出しも重みづけも揃っていない。キャスト決定2段はその整形を**持っていない**。
- つまり R1 が求める「供給の一貫性」は、配線ではなく**消費側の重複と欠落**の問題である。

### キャスト決定段の現在の指示

**`stakeholder-agent.ts:39`**（単一プロンプト・`title` + 事実節のみ）
- 「**直接・間接**の**全**利害関係者を**網羅的**に分析」— 一文に拡散の指示が三重に入っている。この基準で選ぶと、出てくるのは「題材領域の利害関係者」であって「問われていることの当事者」ではない。観測事例の国連 LAWS 担当・防衛装備庁・電力会社 CSIRT・人権 NPO は、「AI のリスク」という題材の利害関係者としては全員正しく、「なぜ米国の AI 企業が減速を主張し始めたのか」という問いの当事者は一人もいない。**プロンプトは指示どおりに働いており、壊れているのは指示のほうである。**
- 「マイノリティや少数意見の立場も忘れずに含める」
- 「専門・意識レベル（engagementLevel）には必ず幅を持たせ、…一般層も含める」「各レベルの人数は固定せず…機械的に何件ずつと割り当てたりしない」
- スキーマ `.min(5)`、上限なし。**ペルソナ数＝ステークホルダー数**（`personasSchema(stakeholders.length)`）。`topic.personaCount` は公開時に数え直す表示用スナップショットで、生成の入力ではない。
- 当事者性を表す語彙は**存在しない**。持っている軸は `minorityLevel` / `engagementLevel` の2つだけで、当事者性は後者へ押し込まれている（「専門家・**当事者層**（high）だけに偏らせないこと」）。`persona-generator-agent.ts:85` でも専門・意識:低 の説明に「生活者・**当事者**の目線から」とあり、同じ語が high と low の双方に現れる。専門家ではないが当事者性は最高、という人物を置ける場所が無い。
- **ステークホルダーが持つ5項目のうち、下流へ届いているのは `role` と `engagementLevel` の2つだけ。** `reason` / `mainInterests` / `minorityLevel` は生成・永続されるだけで、プロンプトにも画面にも下流にも流れない（全コードベースで参照は型定義とテストの固定値のみ）。立場を表示する画面も現在は存在しない（`persona-generation-consolidation` で `StakeholderItem` が消え、`src/lib/stores/stakeholders.svelte.ts` と型だけが残る）。
- `reason`（「なぜこの立場が関係するか」）は、**「問われていることに対してどう当事者か」を書かせる場所として既に存在する**。書かせること自体が選定の規律になるはずだが、誰も読まないため規律として働いていない。R2.4 の設計の手がかりになる。

**`persona-generator-agent.ts:85`**（単一プロンプト・`title` + 立場リスト + 事実節）
- 「**基本的には日本人のペルソナとして生成すること**。ただしテーマが明らかに海外を舞台とする（例: F1、海外スポーツ、国際政治）場合は、そのテーマに合った国籍の人物を含めること」
- `homePrefecture`（都道府県・外国人は空文字）／`familyName` は日本人では空（コード側が割り当てる）／外国人はカタカナ姓名を LLM が返す

### 所在（居住地）の下流での扱い

`homePrefecture` / `nationality` は永続されているが、**下流にほとんど流れていない**。

- 取材（`interview-agent.ts:92-98, 260-266`）の【ペルソナ情報】は 氏名・年齢・職業・立場・背景・関心事 のみ。**所在・国籍を渡していない**（背景文に書かれていれば文中から伝わるだけ）
- 討論（`prompt-formatters.ts` `formatPersonas`）は ID・名前・立場のみ
- アバター（`avatar/avatar-prompt.ts:42`）は `nationality` を服装判断の材料として渡すが、**顔を描かない黒シルエット**なので民族的特徴は出力に現れない
- FE `PersonaItem.svelte` は name / age / role / background を編集表示。**所在・国籍は画面に出ない**
- 公開表示型は `nationality` を持ち込まない（`src/tests/models/persona/persona.types.test.ts:213`、`published-article.test.ts:334` が機械的に検査）

### ギャップの要約

- **R1 は配線済み・消費のみ欠落**。2ファイルのプロンプトに整形結果を足すだけで機械的には満たせる。ただし R1.3（段ごとの分岐を持たない）を素直に満たすなら、3箇所に重複した整形を共有へ畳む判断が要る。
- **R3 が設計上の核心**。「舞台をどう判定し、どこに保持するか」が未決定。ここだけはプロンプト追記で済まない。
- **R4.2 が唯一の型変更**。`homePrefecture: string` 必須／国外は空文字、という契約が国外の所在を表現できない。
- **R2 は既存指示との緊張**。網羅・マイノリティの要求（プロダクトの価値提案そのもの）と、中心を厚くする要求の折り合いが設計判断になる。

## 3. 実装アプローチの選択肢

### Option A: 既存2ファイルのプロンプト拡張のみ（型に触れない）

`stakeholder-agent.ts` と `persona-generator-agent.ts` のプロンプトに、description / sourceContents の整形と、舞台・中心当事者の指示を追記する。`homePrefecture` の契約（国外は空文字）は維持し、国外の所在は `background` の自然文に書かせる。

- **変更対象**: agents 2ファイル、（任意で）`utils/prompt-formatters.ts` に共有整形を追加、テスト2ファイル、検証ハーネス1ファイル
- ✅ 型・永続・FE・移行に一切触れない。R1 / R2 / R3.1-3.3 は満たせる
- ✅ 効果（誰が呼ばれるか）を単一の変数で観測できる
- ❌ **R4.2 を満たさない**。国外の所在が構造として残らず、下流（取材・FE・将来の表示）から参照できない
- ❌ 外国人の氏名は LLM 任せのまま（R4.1 が「傾向に沿う」以上を保証しない）
- ❌ 「日本人＝構造で所在を持つ／外国人＝自然文に書くだけ」という非対称が残る。CLAUDE.md の「欠損データを許容する分岐を実装に残さない」と正面から衝突する

### Option B: 居住地モデルを一般化し、外国人経路を日本人と同格にする

`homePrefecture`（都道府県・国外は空文字）を、国と地域を表現できる所在モデルへ置き換える。日本国内は従来どおり都道府県として解決し、姓の地域割り当てを維持する。外国人の氏名も語彙テーブル化を検討する（`build-surname-tables.ts` の前例）。

- **変更対象**: `types/persona.types.ts` + FE ミラー型、agents 2ファイル、`surname-assignment` の入力契約、`verify-persona-naming`、backfill スクリプト1本、FE/公開型のテスト
- ✅ 仕様どおりの形で実装できる（「所在は全ペルソナが持つ」）。R4 を完全に満たす
- ✅ 下流（取材のペルソナ情報・将来の表示）が所在を構造として参照できる
- ✅ 移行の前例が揃っている（`backfill-persona-home-prefecture.ts` が同型の作業）
- ❌ 影響範囲が FE ミラー型・公開表示型テストまで及ぶ
- ❌ **複数の変数が同時に動く**。キャスト構成が変わったのか、所在モデルが変わったのかを分離して観測できない（steering「検証は変数を1つに絞る」と衝突）
- ❌ 外国人氏名の語彙テーブルは、国籍ごとにデータ源を要し、テーマ次第で必要な国籍が際限なく増える（日本人姓のように有界でない）

### Option C: 2段階（本命を単体で観測 → 構造を仕様どおりに整える）【推奨】

- **第1段階（R1 / R2 / R3）**: 意図の供給と、舞台・中心当事者の決定を正す。プロンプトと国籍判定の分岐のみ。型は触らない。ここで「誰が呼ばれるか」が指示どおりになるかを検証ハーネスで実測する。
- **第2段階（R4 / R5 の残り）**: 第1段階の実測を見て、所在モデルの一般化と外国人氏名の扱い（LLM 任せで足りるか語彙化が要るか）を決め、型変更と backfill を行う。

- ✅ 本命（意図がキャストに効くか）を、型変更のノイズ無しに単体で観測できる
- ✅ 第2段階の判断材料（外国人氏名の分布が実際に狭まるか）が、第1段階の実測で得られる
- ✅ どちらの段階も単独で成立し、途中で止まっても中途半端な構造が残らない
- ❌ 計画が2段階になる分、tasks の設計が要る
- ❌ 第1段階の完了時点では R4.2 が未達のまま（tasks.md に延期理由の明記が必要）

**段階分けの理由を取り違えないこと。** 第2段階を後ろに置くのは、**効果を切り分けて観測するため**であって、型変更や移行を避けるためではない。CLAUDE.md は「移行の手間から逆算して仕様を決めない」「移行が必要になったら移行する」と定めており、Option A を「型に触らなくて済む」ことを理由に選ぶのは禁じられている。第1段階の実測後に第2段階を実施しない選択は無い。

## 4. 規模とリスク

| 区分 | Effort | Risk | 根拠 |
|---|---|---|---|
| 第1段階（R1 / R2 / R3 / R5 の一部） | **M**（3-7日） | **Medium** | 変更ファイル数は少ないが、効果がプロンプトの言葉づかいに依存し、実物での確認が複数周必要 |
| 第2段階（R4 / R5 の残り） | **M**（3-7日） | **Medium** | 型変更と backfill は前例どおりで低リスク。外国人氏名の語彙化は範囲が発散しうる |
| 全体 | **L**（1-2週間） | **Medium** | 単一の技術的難所は無いが、生成品質の判断が人手の確認に依存する |

**リスクの実体は技術ではなく観測**である。「指示どおりのキャストになったか」は機械判定できる部分（国籍・所在・表記）と、人が読んで決める部分（その舞台の人物として自然か、当事者が中心に立っているか）に分かれる。後者を曖昧にしたまま自動ゲートで担保したことにしない（`spec-dependencies.md` の定め）。

## 5. Research Needed（design フェーズへ持ち越す）

1. **舞台の判定をどの段が持つか — 決定済み（2026-09-23）: ステークホルダー段が持つ。**
   立場が存在する場所は立場の属性であって、人物を作る段で毎回テーマから判断し直すものではない。ステークホルダー段が各立場に「その立場が実際に存在する国・地域」を持たせ、ペルソナ段は `engagementLevel` と同様にそれを引き継ぐ。これにより立場ごとに国が異なる状態（R3.5）を構造で表現できる。
   - 既存の「特定の地域を代表する立場（例: 沖縄県民、被災地の住民）では必ずその土地にすること」（`persona-generator-agent.ts:85`）は、本来**立場**の性質を述べた指示であり、この決定で本来の段へ移る。
   - **残る設計詳細（design で決める）**: 場所を `role` 文字列に織り込むか、独立したフィールドとして持つか。同じ職能が複数国に存在する場合（例: AI 開発企業の安全性研究者は米中双方にいる）、立場を国ごとに分けて立てるのか、1つの立場に複数国を持たせるのか。日本国内テーマで都道府県まで立場が持つのか、国だけを持ちペルソナ段が都道府県を決めるのか（姓の地域割り当ての入力になるため、`surname-assignment` の入力契約に直結する）。
2. **当事者性を構造として持つか — 決定済み（2026-09-23）: 持つ。**
   当事者性（その問題が自分の生活・利害にどれだけ直接刺さるか）は、`minorityLevel`（声が届きにくいか）とも `engagementLevel`（専門知識・意識の高さ）とも**独立した軸**である。三者は次のように直交する。

   | 立場（例: 満員電車へのベビーカー持ち込み） | 当事者性 | 少数性 | 専門・意識 |
   |---|---|---|---|
   | ベビーカーを押して通勤する親 | 高 | 高 | 中 |
   | 子育てをしていない満員電車利用者 | 中 | 低 | 低 |
   | 鉄道事業者の現場責任者 | 高 | 低 | 高 |
   | 交通政策の研究者 | 低 | 低 | 高 |
   | 車椅子利用者 | 中 | 高 | 中 |

   **当事者性が高いことと多数派であることは無関係**であり、当事者性が最も高いのがマイノリティ側である場面は普通に起きる（上表の親）。中心＝多数派・声の大きい側と読み替えてはならない。

   **さらに、当事者性は絶対値ではなく「問いに対する相対値」である。** 同じ題材でも問いが変われば当事者は入れ替わる。

   | 問い | 当事者性が高い立場 |
   |---|---|
   | 満員電車へのベビーカー持ち込みは許されるか | ベビーカーを押す親、混雑時の一般利用者 |
   | 鉄道事業者はなぜ明確なルールを出さないのか | 事業者の現場責任者、運輸行政 |
   | ベビーカー論争はなぜ感情的になるのか | 双方の当事者、世論を扱う書き手 |

   したがって軸は「題材に対する当事者性」ではなく「**問われていることに対する当事者性**」として定義しなければならない。題材基準で定義すると、軸を足しても一般論への拡散は止まらない（R2.1-2.2）。

   - **現行プロンプトは当事者性を `engagementLevel` へ押し込んでいる**（是正対象）。`stakeholder-agent.ts:39` は「専門家・**当事者層**（high）だけに偏らせないこと」と書き、`persona-generator-agent.ts:85` は専門・意識:低 の説明で「生活者・**当事者**の目線から」と書く。同じ語が high と low の双方に現れており、軸として成立していない。専門家ではないが当事者性は最高、という人物（上表の親）を正しく置ける場所が現行の型に無い。
   - **読み手（本 spec の範囲内）**: (a) ステークホルダー生成自身 — 値を返させること自体が「当事者性を意識して立場を立てる」強制になる（R2.1）。(b) ペルソナ生成 — 当事者性の高さを「切実さ」として描く。専門性の高さ（持論・専門的視点）とは別の描き分けにする。あわせて `engagementLevel` の説明から「当事者」の語を外し、軸の混同を解消する。
   - **読み手（本 spec の範囲外）**: 討論の発言機会。話者選択は意欲評価のスコアで動いており、そこへ軸を足すのは討論設計そのものの変更になる。本 spec では決めない。**ただし価値との衝突を理由に排除するのではない** — 当事者性で厚みを付けることは「声が届きにくい立場の可視化」と衝突しない。
   - **`minorityLevel` の死蔵は軸の無意味さを示さない。** 現状 `minorityLevel` は生成・永続されるだけで誰も読んでいないが、上表が示すとおり少数性はペルソナ生成・討論に効くべき情報である。死蔵は配線の欠落であって軸の不要性ではない。本 spec で当事者性を配線する際、`minorityLevel` の配線も併せて是正するかを design で判断する。
   - **残る設計詳細（design で決める）**: 値域（`minorityLevel` / `engagementLevel` と同じ high/medium/low に揃えるか）、フィールド名、ペルソナへ引き継ぐか（`engagementLevel` は引き継いでいる）。
3. **「問われていること」をどう取り出すか** — R2 の選定基準は問いに依存するが、`description` は自由記述で、複数の問いを含むことも、問いの形で書かれないこともある（観測事例は「その背景に何があるのか」「何を考えているのか」の2問＋「周囲を取り巻くプレイヤー」への言及を含む）。(a) ステークホルダー生成に自然文のまま渡して解釈させる、(b) 問いを明示的に取り出す段を設ける、の2案。(b) は論点生成（`chapter-agent`）が既に description を「方向性」として扱っていることと重複しうるため、責務の切り分けが要る。
4. **description の重みづけの統一** — `chapter-agent` の「方向性（最優先）」と他2箇所の「詳細説明」のどちらへ揃えるか。共有整形に畳む場合、段ごとに重みが違ってよいのか（キャスト決定では「最優先」、導入締めでは「詳細説明」など）を決める必要がある。R1.3 と R6.5 の両立点。
5. **外国人氏名を LLM に任せてよいか** — 日本人姓で観測された「分布が狭まり珍しい姓が再出現する」問題が国籍別にも起きるかを、第1段階の実測（`inspect-persona-names.ts` の拡張）で確かめる。起きるなら語彙テーブル化だが、国籍の範囲をどう有界にするかが未解決。
6. **場所の持ち方 — 決定済み（2026-09-23）: 所在を国・都道府県の任意項目（`country?` / `prefecture?`）として持ち、`nationality` は `country` へ改名して残す。**
   ステークホルダー生成がテーマの決めている範囲だけを埋め、ペルソナはそれを変えず、空いている項目だけを必要に応じて補う。テーマが土地を問わない立場はどちらも持たない。市区町村・州や、国籍と居住国が異なる来歴は、項目を増やさず `background` の自然文が受け持つ。
   - **所在の解釈をコードに持たせない。** `prefecture` は 47 件の enum として生成スキーマで直接受け取るため、表記ゆれの正規化（`normalizePrefecture`）が生成経路から外れる。コードは値の有無を見るだけにする。
   - **日本人の名前決定に地域性を反映する仕組みは生かす。** `assignSurnames`・姓テーブル・地域区分は無変更で、入力が `homePrefecture` から `prefecture` へ替わるだけ。都道府県が決まっていない人物は県を限定せず全国の語彙から引く。姓そのものを LLM に選ばせる経路は持たない。
   - 移行は `homePrefecture` → `prefecture`、`nationality` → `country` の改名。値の解釈を伴わず、国外ペルソナの国も残るため失われる情報が無い。詳細は `research.md` の Design Decisions を参照。
   - **採用しない経路**: 自由記述の `region` 1本にして `nationality` を撤廃する案。姓の地域性が壊れる（自由記述は都道府県として読めず全国姓へ縮退する）ため破棄した。この経路の記述を根拠に実装しないこと。
7. **検証ハーネスの対象範囲** — `verify-persona-naming.ts` は立場リストをハードコードしており、ステークホルダー段を呼んでいない。R2（当事者が中心に立つか）を検証するには、テーマ文からステークホルダー生成を含めて通す必要がある。既存ハーネスを拡張するか、別ハーネスを立てるか。
8. **論点生成への波及の確認** — 論点の片系統（`chapter-agent.ts:397` の personaIssues）はキャストの立場を入力にしている。キャストが正されたとき論点が実際に変わることを、どの段で確認するか。

## 6. design フェーズへの推奨

- **推奨アプローチ: Option C（2段階）**。段階分けの理由は効果の切り分けであり、移行回避ではない（第2段階を落とさない）。
- **決定済みの前提（2つともスキーマに影響する）**:
  1. 舞台の判定はステークホルダー段が持つ（Research Needed 1）。保持形は上記 6 のとおり `country?` / `prefecture?` の任意項目に決定済み。
  2. 当事者性は構造として持つ（Research Needed 2）。design は値域・フィールド名・ペルソナへの引き継ぎと、`engagementLevel` から当事者性の語を分離する範囲を決める。
- **踏襲すべき既存パターン**: `chapter-agent.ts` の `buildTopicContextSection`（整形と重みづけ）、`tests/agents/chapter-agent.test.ts`（プロンプト反映のテスト）、`scripts/backfill-persona-home-prefecture.ts`（移行）、`verify-persona-naming.ts`（本番同一経路の検証）。
- **壊してはならない契約**: 日本国内テーマの姓の地域割り当て（`surname-assignment` とそのテスト）、姓を LLM に選ばせないこと（日本語の姓名の人物は `familyName` を空で返す指示）、`sourceTag` による由来の突合、公開表示型が所在を持ち込まないこと、章立てが description を最優先で扱うこと。
