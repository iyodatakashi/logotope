# Implementation Plan

- [x] 1. Foundation: リセットのフェーズ中立化とサーバ側破棄ヘルパー
- [x] 1.1 編集リセットのフェーズ書き込みを除去する
  - 編集リセットが編集成果物の破棄のみを行い、フェーズ状態（進捗フェーズ・ステータス）を書き換えないようにする
  - 呼び出し前のフェーズ状態がリセット後もそのまま保持される
  - docstring を実態（フェーズは書き換えない）に合わせる
  - 単体テスト: 編集リセット実行後にフェーズ状態への書き込みが発生しないこと
  - _Requirements: 1.1, 1.2, 1.3, 3.6_

- [x] 1.2 下流データをサーバ側で破棄する共通ヘルパーを整備する
  - ステークホルダー・ペルソナ・章立て（付随分析含む）をサーバから破棄できるようにする（討論・編集の破棄は既存を流用）
  - 破棄範囲は現行のクライアント/サーバのリセットと1対1で一致させる
  - 「既に無いものを消す」は no-op として扱い、同入力で何度実行しても同結果になる（冪等）
  - 単体テスト: 対象＋下流のみを削除し、他フェーズのデータを残すこと
  - _Requirements: 3.1, 6.3_

- [x] 2. Core: 各再生成をサーバ権威の単一操作にする（フェーズ確定→破棄→生成/投入）
- [x] 2.1 (P) ペルソナ再生成をサーバ権威化する
  - 単一の呼び出しで「対象フェーズを実行中に確定（単一ドキュメントの update 1回・トランザクション不使用）→ 自層＋下流破棄 → 最初の段を投入」をこの順序で実行する
  - フェーズ確定時に新しい世代番号を発行し、旧世代の残タスクを無効化する（中間の窓を作らない）
  - 初回生成では破棄が no-op になり同一経路を通る
  - フェーズ確定後に破棄／投入が失敗した場合、対象フェーズのまま停止状態にする（下流の完了状態へ戻さない）
  - 観測可能: approved 起点から呼んでも、呼び出し直後に対象フェーズが実行中になり下流が完了表示にならない
  - _Requirements: 3.1, 3.2, 3.4, 3.5, 3.6, 6.2_
  - _Boundary: startPersonaGeneration onCall_
  - _Depends: 1.2_

- [x] 2.2 (P) 事実リサーチ再生成をサーバ権威化する
  - 「fact-research を実行中に確定 → 全下流破棄 → 生成 → 完了確定」をこの順序で所有する
  - フェーズ確定後の失敗時は対象フェーズのまま停止状態にする
  - 観測可能: approved 起点の再生成でも下流フェーズが完了表示にならない
  - _Requirements: 3.1, 3.2, 3.4, 6.2_
  - _Boundary: generateFactResearch onCall_
  - _Depends: 1.2_

- [x] 2.3 (P) 章立て再生成をサーバ権威化する
  - 「chapters を実行中に確定＋新世代 → 旧章立て・付随分析＋下流破棄 → 生成」をこの順序で所有する
  - フェーズ確定後の失敗時は対象フェーズのまま停止状態にする
  - 観測可能: approved 起点でも下流（討論・編集）が完了表示にならない
  - _Requirements: 3.1, 3.2, 3.4, 3.5, 6.2_
  - _Boundary: generateChapters onCall_
  - _Depends: 1.2_

- [x] 2.4 (P) 討論再生成をサーバ権威化する
  - 「debate を実行中に確定＋新世代 → 討論付随データ＋下流編集破棄 → 開始」をこの順序で所有する
  - フェーズ確定後の失敗時は対象フェーズのまま停止状態にする
  - 観測可能: 下流（編集）が完了表示にならない
  - _Requirements: 3.1, 3.2, 3.4, 3.5, 6.2_
  - _Boundary: startDebate onCall_
  - _Depends: 1.2_

- [x] 3. Integration: クライアント再生成ハンドラの単純化と即時フィードバック
- [x] 3.1 各再生成画面を単一サーバ操作の呼び出しへ単純化する
  - 事実リサーチ・ペルソナ・章立て・討論の各再生成ハンドラを「確認ダイアログ → サーバ操作を1回呼ぶ」に置き換える
  - 複数リセットの順次実行と「起動処理を最後に呼んで phase を後勝ちさせる」旨のコメント・前提を撤去する
  - 呼び出し順序に依存せず最終フェーズ状態が正しくなる
  - 観測可能: 各ハンドラがサーバ操作を1回だけ呼ぶ
  - _Requirements: 3.2, 4.1, 4.2_
  - _Depends: 2.1, 2.2, 2.3, 2.4_

- [x] 3.2 再生成押下直後に旧データを即時に隠す表示制御を追加する
  - 破棄がサーバ移設されても旧データが即時に消えるよう、各画面に表示専用の再生成中フラグを持たせる（実データ削除はサーバが権威的に行う）
  - フラグ解除は呼び出し完了ではなく実同期状態に連動させる（対象フェーズが実行中かつ旧データが実際に消えた／新データ到着時に解除）ことで、往復後の一瞬の再表示を防ぐ
  - 観測可能: 再生成押下直後、同期反映を待たずに旧データが隠れ、その後ちらつかずに新状態へ移る
  - _Requirements: 3.3, 6.3_
  - _Depends: 3.1_

- [x] 3.3 編集やり直しを開始操作のみへ単純化する
  - 編集画面のやり直しを、成果物破棄と実行中化を担う開始操作のみで完結させる（明示的な編集リセット呼び出しを外す）
  - 最終状態が編集フェーズ・実行中に到達し、旧記事が破棄されている
  - editing は最終フェーズのため先行フェーズ確定・下流破棄を行わない
  - _Requirements: 2.2, 3.7, 6.1_

- [x] 4. 重複・未使用コードの整理
- [x] 4.1 重複するペルソナリセットを一本化する
  - フェーズ状態を書き換えてしまう未配線のペルソナリセット（ストア側）を削除し、フェーズを書かない実装へ一本化する
  - どの経路から呼んでもペルソナのリセットがフェーズ状態を書き換えない
  - 削除メソッドに対応する既存テストを整合させる
  - _Requirements: 5.1, 5.2, 1.3_

- [x] 4.2 未使用化したリセット経路を削除する
  - サーバ権威化・ハンドラ単純化で未使用になったクライアント側リセットラッパ、および単独の編集リセット呼び出し口を、実参照が無いことを確認のうえ削除する
  - フェーズ遷移を書く主体が起動・前進・明示停止の処理だけに限定される
  - _Requirements: 2.1, 4.1_
  - _Depends: 3.1, 3.3_

- [x] 5. 命名と責任範囲の一致（挙動変更と分離した改名波及）
- [x] 5.1 (P) 単一状態名でフェーズも書くセッターを改名する
  - 状態設定に見えて進捗フェーズも書くセッターの名前を、フェーズを書くことが読める名に改める（呼び出し箇所を網羅して一括で更新）
  - 観測可能: 改名後もフェーズ確定の挙動が不変（回帰テスト green）
  - _Requirements: 7.1, 7.3_
  - _Boundary: topic model_

- [x] 5.2 (P) 状態設定名で世代番号まで発行する討論の遷移関数を改名する
  - 状態名に見えて新しい世代番号まで発行する討論フェーズの遷移関数を、その責務が読める名に改め、docstring で世代発行を明示する（呼び出し箇所を網羅）
  - 観測可能: 改名後も討論の実行中確定・世代発行が不変
  - _Requirements: 7.1, 7.3_
  - _Boundary: debate lifecycle_

- [x] 5.3 (P) 取材名でトピックのフェーズを書く操作を是正する
  - 取材の開始/停止に見えてトピックのフェーズ状態を書く操作を、フェーズを書く旨が読める名へ改める（最小対応の場合は docstring で根拠を明示）
  - _Requirements: 7.3_
  - _Boundary: personas store_

- [x] 5.4 (P) 名前が広い副作用を隠す非フェーズ系メソッドに処置区分を反映する
  - 監査で「現状維持＋根拠」とした各メソッド（取得系の書き込み・局所名でラン全体を確定・破棄名で再初期化・公開時の再集計・保存時の削除/巻き戻し 等）に、実責務を明示する docstring を付す（または別仕様への切り出しを注記する）
  - 観測可能: 対象メソッドが処置表どおり「是正／現状維持＋根拠／別仕様」のいずれかで明示処置され、未処置放置が無い
  - _Requirements: 7.2, 7.4_

- [x] 6. Validation: 回帰・堅牢性の検証
- [x] 6.1 破棄集合パリティを検証する
  - 各サーバ権威操作の破棄範囲が、整理前のクライアント/サーバのリセット集合と完全一致することを onCall 単位で検証する
  - 消し残し・消しすぎがないことをテストで固定する
  - _Requirements: 6.3_
  - _Depends: 2.1, 2.2, 2.3, 2.4_

- [x] 6.2 approved 起点のフラッシュ根絶・即時クリア・失敗時停止を検証する
  - 前進済み（approved）状態から各再生成を開始し、下流フェーズが完了表示にならないことを検証する
  - 押下直後の即時クリアが効き、往復後にちらつかないことを検証する
  - フェーズ確定後の失敗で対象フェーズのまま停止状態になり、実行中固着・下流後退が起きないことを検証する
  - _Requirements: 3.2, 3.3, 3.4_
  - _Depends: 3.1, 3.2_

- [x] 6.3 最終状態の回帰を検証する
  - 各再生成カスケード完了後に対象フェーズが実行中へ到達すること、編集やり直しが編集フェーズ・実行中＋旧記事破棄で完了することを検証する
  - _Requirements: 6.1, 6.2_
  - _Depends: 2.1, 2.2, 2.3, 2.4, 3.3_
