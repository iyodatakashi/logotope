# Requirements Document

## Project Description (Input)
討論のチャプター処理タスク（`runChapter` / `executeChapterTask`）が、**同一 runId のまま二重に並走**することで、同じ発言者のターンが連続して二重生成される不具合を解消する。

観測された症状: 討論ログで、指名されたペルソナA の発言が2回連続し、その後 A が指名したペルソナB の発言も2回連続する、という規則的な重複が発生した。エンゲージメント表（直前話者を除外）と「次の指名」「→選択（= 次の話者）」の値を突き合わせると、`…facilitator, コヴァレンコ_A, コヴァレンコ_B, アリョーナ_A, アリョーナ_B…` のように、2つの実行インスタンスが同一の初期状態（Firestore からロードしたターン列）から同じ手順で発言を生成し、全ターンを2部ずつ arrayUnion で書き込んでいると考えると全数値が一致する。

根本原因の仮説:
- `runChapter` は Cloud Tasks（`retryConfig.maxAttempts: 3`, `timeoutSeconds: 540`, at-least-once 配信）で動作する。元インスタンスがタイムアウト後もバックグラウンドで実行を続けたまま、Cloud Tasks がリトライ／重複配信を起動すると、2つの実行が並走しうる。
- 既存の世代ガード（`debate-run-isolation` spec / `addTurn` の runId 照合）は「**別の** runId」を弾くだけで、リトライは**同一 runId** を引き継ぐため照合が常に成功し、二重書き込みを止められない。
- `addTurn` は毎回新しい nanoid でターンを `arrayUnion` するため、重複排除も働かない。
- 単一実行ではこの連続並びは構造上発生しえない（指名は直前ターンを読み、本人の応答は別人を指名するため）ことから、二重実行が原因と特定できる。

ゴール: 同一チャプターの処理が同時に複数走っても、各「ターン位置（発言枠）」が高々1回だけ Firestore に書き込まれることを保証する（冪等なターン追記 / 楽観的並行制御 等）。`debate-run-isolation`（別世代のブロック）とは別レイヤーの、**同一世代内の重複実行**に対する防御を定義する。

対象外（想定）: 旧 Cloud Function invocation の強制終了・キャンセル（Cloud Tasks 仕様上不可）、別 runId 間の競合（既存 `debate-run-isolation` の責務）。

## Introduction

討論パイプラインの各チャプターは Cloud Tasks タスク `runChapter`（`executeChapterTask`）として実行され、**1チャプター分のターンループ全体を1回の function 実行の中で回す**現構造になっている。各実行はチャプター冒頭で Firestore からターン列を一度だけロードし、以降はインメモリ状態を進めながら `addTurn`（`arrayUnion` + 毎回新規 nanoid）でターンを追記する。

Cloud Tasks は at-least-once 配信であり、かつ `onTaskDispatched` の実質上限である30分（Cloud Tasks の dispatch deadline）を超えると、旧インスタンスがバックグラウンドで処理を続けたまま Cloud Tasks がリトライ／重複配信を起動する。その結果、**同一 runId を持つ同一チャプターの実行が一時的に複数並走**し、各実行が同じロード地点から同じ手順で発言を生成して、全ターンを実行ごとに重複追記する（「同じ発言者が連続する」症状）。既存の `runId` 世代ガードは**別世代**の書き込みのみを弾くため、同一 runId のリトライ／重複実行は防げない。

この spec は、根本対策として**チャプター処理を「1ターン単位の再入可能なタスク」に再構成する**。各タスクは起動のたびに Firestore から討論状態を再構築し、1ターン（ペルソナまたはファシリテーター）だけを生成して**期待ターン位置の原子的照合のもとで高々1回だけ追記**し、続きを次タスクとして enqueue する。これにより、(1) 長時間の単一実行が引き起こす並走の窓をほぼ消し、(2)「ロード1回→インメモリ行進→並走時に2本へ分岐」という故障モードを構造的に除去し、(3) 冪等性を単一の原子チェックに帰着させ、(4) 30分上限の制約から解放される。`debate-run-isolation`（別 runId の旧世代ブロック）とは独立した、補完的な防御層と位置づける。

## Boundary Context

- **In scope**:
  - チャプター処理を「1チャプター=1実行のターンループ」から「1ターン=1タスクの再入可能な実行」へ再構成する
  - 各タスク起動時に Firestore から討論状態（ターン列・queuedIntents・silenceMap・speakCount 等）を再構築する
  - ターン追記時の「期待ターン位置」と Firestore 上の最新位置の原子的な照合・追記（ペルソナターン・ファシリテーターターンの双方）
  - 重複・陳腐タスクの安全な no-op 終了
  - 章継続・章終了・次章遷移・終端処理（クロージング・事後コメント）の永続状態駆動化と冪等化
  - 再構成前後での討論ロジックの行動等価性
- **Out of scope**:
  - 旧 Cloud Function invocation の強制終了・キャンセル（Cloud Tasks 仕様上不可）
  - 別 runId 間の競合（`debate-run-isolation` の責務）
  - ターンの読み取り処理・UI 表示ロジック
  - LLM 生成内容そのものの決定性（同一入力でも文言は変わりうる）
- **Adjacent expectations**:
  - 既存 `debate-run-isolation` の runId 世代照合（別世代ブロック）は維持し、本 spec のガードはそれと独立した責務として追加する
  - 既存の `isDebateActive`（停止チェック）の責務には踏み込まない
  - Firestore の `topics/{topicId}/chapters/{chapterId}` が討論状態・ターン位置の正（source of truth）となる
  - チャプター単位のタスクチェーン（`enqueueChapterTask`）の既存パターンを、ターン単位まで拡張する

## Requirements

### Requirement 1: ターン単位の再入可能な処理

**Objective:** 討論の運用者として、チャプター処理が1ターン単位の再入可能なタスクに分割されることで、長時間の単一実行に起因する並走と分岐をなくしたい。

#### Acceptance Criteria
1. The チャプター処理パイプライン shall 1回のタスク実行で生成・追記するターンを高々1つ（1ペルソナターンまたは1ファシリテーターターン）に限定する。
2. When ターン処理タスクが起動する, the チャプター処理パイプライン shall Firestore から討論状態（ターン列・queuedIntents・silenceMap・speakCount 等）を再構築してから当該ターンの処理を行う。
3. The チャプター処理パイプライン shall タスク間でインメモリ状態が引き継がれることを前提にせず、各タスクが永続データのみから自身の処理を決定できるようにする。
4. When 1ターンの追記が成功した, the チャプター処理パイプライン shall 続きの処理を次のタスクとして enqueue する。

---

### Requirement 2: 冪等なターン追記（期待位置の原子照合）

**Objective:** 討論の運用者として、各ターンが期待位置の原子的照合のもとで追記されることで、重複配信や並走があっても各発言枠が高々1回だけ永続化されるようにしたい。

#### Acceptance Criteria
1. The チャプター処理パイプライン shall 各ターン処理タスクに、追記すべきターン位置（期待するターンインデックス等）を識別できる情報を持たせる。
2. The チャプター処理パイプライン shall ターン位置の照合と当該ターンの追記を、Firestore のトランザクションまたは同等の原子的操作として不可分に実行する。
3. When 2つ以上のタスクが同一のターン位置への追記を同時に試みる, the チャプター処理パイプライン shall そのうち高々1つのみを成功させ、他方の追記を拒否する。
4. While 同一世代の複数のタスクが並走している間, the チャプター処理パイプライン shall 各ターン位置（発言枠）に対し高々1つのターンのみが Firestore に永続化されることを保証する。

---

### Requirement 3: 重複・陳腐タスクの安全な no-op 終了

**Objective:** 討論の運用者として、重複配信された／世代遅れのタスクが安全に何もせず終了することで、二重生成や不正な討論停止・リトライを防ぎたい。

#### Acceptance Criteria
1. If タスクが起動時に、自身の担当ターン位置が既に Firestore 上で埋まっている（重複配信・先行追記）ことを検出した, then the チャプター処理パイプライン shall 当該ターンを書き込まず処理を終了する。
2. When 重複・陳腐を理由にタスクを終了する, the チャプター処理パイプライン shall エラーをスローせず正常終了し、討論を停止状態（`phaseStatus`）に遷移させない。
3. When 重複・陳腐を理由にタスクを終了する, the チャプター処理パイプライン shall Cloud Tasks のリトライを誘発せず、かつ重複した続きタスクを enqueue しない。

---

### Requirement 4: 章進行・終端処理の永続状態駆動と冪等性

**Objective:** 討論の運用者として、章の継続・終了・次章遷移・終端処理が永続状態から判断され冪等であることで、二重 finalize やクロージング・事後コメントの重複を防ぎたい。

#### Acceptance Criteria
1. When 各ターン処理タスクが完了する, the チャプター処理パイプライン shall 章継続・章終了・次章遷移・討論終端のいずれに進むかを、再構築した永続状態に基づいて決定する。
2. The チャプター処理パイプライン shall オープニング・章導入・章まとめ・クロージングを含むすべてのファシリテーターターンの書き込みに、Requirement 2 と同一の位置照合・原子的追記を適用する。
3. When チャプターを完了状態に遷移させる, the チャプター処理パイプライン shall 既に完了済みのチャプターに対して終端処理（クロージング・事後コメント生成・`phaseStatus` 更新・次章 enqueue）を二重に実行しない。
4. If 同一世代の別タスクが既に当該チャプターの終端処理を実施した後で自身が終端処理に到達した, then the チャプター処理パイプライン shall クロージング・事後コメントを重複生成しない。

---

### Requirement 5: 再構成前後の行動等価性

**Objective:** 討論の運用者として、per-turn 化リファクタの前後で討論ロジックが等価であることで、討論の質や進行が意図せず変わらないようにしたい。

#### Acceptance Criteria
1. The チャプター処理パイプライン shall 再構成後も、話者決定の優先順位（指名 > キュー > スコア）・エンゲージメント評価・ファシリテーター介入・章終了カウントの判定ロジックを再構成前と等価に保つ。
2. The チャプター処理パイプライン shall 章末に未応答の指名が残る場合の応答ターン（+1ターン許容）の意味論を再構成前と等価に保つ。
3. The チャプター処理パイプライン shall 1ターンあたりの処理（全員のエンゲージメント評価・直前話者の除外・キュー更新等）の結果が、再構成前の単一ループ版と論理的に等価になるようにする。

---

### Requirement 6: 既存世代ガードとの共存と後方互換

**Objective:** 討論の運用者として、per-turn 化と冪等追記が既存の runId 世代ガードや停止チェックを壊さずに導入されることで、既存の競合対策を維持したい。

#### Acceptance Criteria
1. The チャプター処理パイプライン shall 既存の runId による世代照合（別 runId の旧世代ブロック）を維持したまま、同一 runId 内の冪等追記を追加で適用する。
2. The チャプター処理パイプライン shall 同一世代内の冪等追記を、既存の `isDebateActive` 停止チェックおよび runId 世代照合とは独立した責務として扱う。
3. Where ターン位置照合に必要なメタデータがタスクまたは Firestore 上に存在しない（レガシー・移行期のデータ）, the チャプター処理パイプライン shall 位置照合をスキップしてターン書き込みを許可する。

---

### Requirement 7: 正常系の非阻害

**Objective:** 討論の運用者として、並走が発生していない通常実行で冪等追記が副作用を持たないことで、正当なターンが失われないようにしたい。

#### Acceptance Criteria
1. While 単一のタスク系列のみが順次動作している（並走なし）, the チャプター処理パイプライン shall すべてのターンを通常どおり書き込み、冪等照合によって正当なターンを脱落させない。
2. The チャプター処理パイプライン shall 位置照合によるターン書き込み拒否を、重複配信または同一世代の並走が実際に発生している場合に限定する（誤検知による正当なターンの破棄を行わない）。
