# Requirements Document

## Project Description (Input)
ステークホルダー生成、ペルソナ生成、ペルソナ取材を1画面にまとめたい。具体的には、、ステークホルダーとペルソナが左右対になっている画面。左がステークホルダー、右がペルソナ。まずステークホルダーが生成される。採用するステークホルダーのチェックボックスをONにし（デフォルトはON）、ペルソナ生成ボタンを押すと、ステークホルダーに対応するペルソナが生成される。チェックを入れていないステークホルダーのペルソナは生成されない。さらにペルソナ取材ボタンを押すと、生成されたペルソナの取材が実行される。

## Introduction

現在、討論生成パイプラインのうち「ステークホルダー調査」「ペルソナ生成」「ペルソナ取材」は、それぞれ独立したフェーズ画面（`stakeholders` / `personas` / `interviews`）に分かれており、各フェーズを承認してタブ遷移しながら順に進める構成になっている。

本フィーチャーは、この3つの操作を **1つの統合ワークスペース画面** に集約する。画面は、1つのステークホルダー（左）とその対応ペルソナ（右）を1つの左右セット（行）とし、この行を縦に並べて構成する。画面全体を左右2カラムに分割するのではなく、「ステークホルダー↔対応ペルソナ」の対応関係を行ごとに横並びで示すことで、どの立場からどの人物像が生成されたのかを一望できるようにする。管理者は同一画面上で「ステークホルダー生成 → 採用ステークホルダーの選択 → ペルソナ生成 → ペルソナ取材」を連続して実行できる。

従来と異なる中核的な新機能は、**ステークホルダー単位の採用選択**である。各ステークホルダーに採用チェックボックス（既定ON）を設け、チェックONのステークホルダーだけに対応するペルソナを生成し、チェックOFFのステークホルダーのペルソナは生成しない。これにより、管理者は生成前に立場の取捨選択を行える。

また、フェーズは既存どおり `stakeholders` / `personas` / `interviews` の3つを据え置くが、**明示的な承認（approve）操作は画面から廃止**し、フェーズ境界の承認（＝次フェーズへの前進）を**次の操作に暗黙的に畳み込む**。具体的には、「ペルソナ生成」実行時にステークホルダーを承認し、「ペルソナ取材」実行時にペルソナを承認し、「章立てへ進む」操作時に取材を承認する。管理者は承認ボタンを個別に押す必要がなく、生成・取材・前進の操作だけで工程が進む。

## Boundary Context

- **In scope**:
  - ステークホルダーと対応ペルソナを1行の左右セットとし行を縦に並べる統合ワークスペース画面のレイアウトと導線
  - ステークホルダー生成 / ペルソナ生成 / ペルソナ取材の同一画面からの実行と状態表示
  - ステークホルダー単位の採用選択（チェックボックス、既定ON）と、選択に基づく選択的ペルソナ生成
  - ステークホルダーと生成ペルソナの対応関係の可視化
  - 既存 `stakeholders` / `personas` / `interviews` 画面の統合画面への置き換え
- **Out of scope**:
  - 章立て（`chapters`）以降のフェーズの挙動
  - 取材・信念生成の内部アルゴリズム、ペルソナ生成プロンプトの内容
  - ステークホルダー生成・取材の生成品質そのもの
- **Adjacent expectations**:
  - 既存のフェーズモデル（`fact-research → stakeholders → personas → interviews → chapters → …` の進行順・`phaseStatus`）と矛盾しないこと
  - 既存の生成 API（`generateStakeholders` / `generatePersonas` / `runInterview`）およびそのサーバ権威なステータス確定の仕組みと整合すること
  - 既存の永続データ構造（`topics/{id}/stakeholders/0`、`topics/{id}/personas/*`）と互換であること

## Requirements

### Requirement 1: 統合ワークスペース画面（左右対レイアウト）
**Objective:** 管理者として、ステークホルダー・ペルソナ・取材を1画面で扱いたい。フェーズごとの画面遷移なしに、立場から人物像・取材まで一望して作業を進めたいからである。

#### Acceptance Criteria
1. The system shall 1つのステークホルダー（左）とその対応ペルソナ（右）を1つの左右セット（行）として表示し、その行を縦方向に並べて統合ワークスペース画面を構成する。
2. The system shall ステークホルダー生成・ペルソナ生成・ペルソナ取材の3操作を、同一の統合ワークスペース画面から実行できるようにする。
3. When ステークホルダーとそれに対応するペルソナがともに存在する, the system shall そのステークホルダーと対応ペルソナを同一行の左右に対応づけて表示する。
4. While ペルソナが未生成のステークホルダーが存在する, the system shall そのステークホルダーの行の右側を空白のままとする（プレースホルダー表示は行わない）。
5. The system shall 統合画面において、各操作の現在の実行状態（未実行 / 実行中 / 完了 / 停止）を管理者が判別できるように表示する。

### Requirement 2: ステークホルダー生成
**Objective:** 管理者として、テーマに関係する多様な立場を統合画面の左カラムに生成したい。ペルソナ生成の起点となる立場一覧を用意するためである。

#### Acceptance Criteria
1. When 管理者がステークホルダー生成（調査開始）を実行する, the system shall テーマに基づくステークホルダー一覧を生成し、各ステークホルダーを1行ずつ（行の左側に）表示する。
2. While ステークホルダー生成が実行中である, the system shall 実行中であることを示す表示を行い、生成完了まで結果領域に進行中を示すプレースホルダーを表示する。
3. When ステークホルダー生成が完了する, the system shall 生成された各ステークホルダーを1行ずつ縦に並べて表示する。
4. If ステークホルダー生成が失敗する, then the system shall 停止状態を示し、再実行（再生成）できるようにする。
5. Where 既にステークホルダーが生成済みである, the system shall 現在のステークホルダーおよび以降の下流データ（ペルソナ・取材）を破棄したうえで再生成できるようにする。

### Requirement 3: ステークホルダーの採用選択
**Objective:** 管理者として、生成されたステークホルダーのうちペルソナ化する立場を取捨選択したい。すべての立場を人物化するのではなく、討論に必要な立場だけを採用したいからである。

#### Acceptance Criteria
1. When ステークホルダーが行に表示される, the system shall 各ステークホルダー（各行の左側）に採用可否を切り替えるチェックボックスを付与する。
2. The system shall 各ステークホルダーの採用チェックボックスの初期状態を ON（採用）とする。
3. When 管理者がステークホルダーの採用チェックボックスを切り替える, the system shall そのステークホルダーの採用状態を即座に反映する。
4. If ペルソナ生成の時点で採用されているステークホルダーが1件も存在しない, then the system shall ペルソナ生成を実行させず、少なくとも1件の採用が必要であることを管理者に示す。

### Requirement 4: 選択ステークホルダーに基づくペルソナ生成
**Objective:** 管理者として、採用したステークホルダーだけからペルソナを生成したい。採用した立場に対応する人物像だけを各行の右側に揃えたいからである。

#### Acceptance Criteria
1. When 管理者がペルソナ生成を実行する, the system shall 採用（チェックON）されているステークホルダーのみに対応するペルソナを生成する。
2. If ステークホルダーの採用チェックが OFF である, then the system shall そのステークホルダーに対応するペルソナを生成しない。
7. When 管理者がペルソナ生成を実行する, the system shall 明示的な承認操作を要求せず、ステークホルダーフェーズを承認済み（`personas` フェーズへ前進した状態）にしたうえでペルソナ生成を行う。
3. When ペルソナが生成される, the system shall 各ペルソナをその由来ステークホルダーに対応づけ、そのステークホルダーと同一行の右側に表示する。
4. While ペルソナ生成が実行中である, the system shall 実行中であることを示す表示を行う。
5. If ペルソナ生成が失敗する, then the system shall 停止状態を示し、再実行できるようにする。
6. When 採用選択を変更してペルソナ生成を再実行する, the system shall 生成結果を現在の採用選択に一致させ、その際に下流データ（取材記録およびそれ以降の成果物）を破棄する。

### Requirement 5: ペルソナ取材の実行
**Objective:** 管理者として、生成されたペルソナに対して取材を実行したい。各ペルソナの信念・背景を裏付ける取材レコードを揃え、討論の基礎を作るためである。

#### Acceptance Criteria
1. When 管理者がペルソナ取材を実行する, the system shall 生成済みの全ペルソナに対して取材を実行する。
6. When 管理者がペルソナ取材を実行する, the system shall 明示的な承認操作を要求せず、ペルソナフェーズを承認済み（`interviews` フェーズへ前進した状態）にしたうえで取材を行う。
2. While ペルソナ取材が実行中である, the system shall 各ペルソナまたは全体の取材進捗（完了 / 待機中 / エラーの件数など）を表示する。
3. If 一部のペルソナの取材が失敗する, then the system shall 失敗を示し、未完了のペルソナの取材を再実行できるようにする。
4. When 全ペルソナの取材が完了する, the system shall 取材完了を示す。
5. The system shall ペルソナが1件も生成されていない状態ではペルソナ取材を実行させない。

### Requirement 6: 操作順序とフェーズ進行の整合（承認の暗黙化）
**Objective:** 管理者として、承認ボタンを個別に押すことなく、統合画面での生成・取材・前進の操作だけで既存の3フェーズ（`stakeholders` / `personas` / `interviews`）が矛盾なく進み、取材完了後に次工程（章立て）へ進みたい。工程を簡潔に保ちつつパイプライン全体の一貫性を保つためである。

#### Acceptance Criteria
1. The system shall フェーズ境界の承認（approve）を独立したボタン操作としては提供せず、次の生成・取材・前進の操作に暗黙的に含めて実行する。
2. While ステークホルダーが未生成である, the system shall ペルソナ生成を実行させない。
3. While ペルソナが未生成である, the system shall ペルソナ取材を実行させない。
4. When 管理者が「章立てへ進む」操作を実行する, the system shall 取材フェーズを承認済みにして章立て（`chapters`）フェーズへ前進させる。
5. The system shall 統合画面に表示する各操作の状態を、トピックのフェーズ状態（`phase` / `phaseStatus`）と矛盾しないように導出する。
6. Where ステップナビゲーション等の全体進行UIが存在する, the system shall 統合画面への集約後もパイプライン全体の進行状況を管理者が把握できるようにする。

### Requirement 7: 既存フェーズ画面からの移行
**Objective:** 管理者として、統合画面が従来の3つの個別画面を過不足なく置き換えることを期待する。移行によって既存データや操作が失われないためである。

#### Acceptance Criteria
1. The system shall 既存の `stakeholders` / `personas` / `interviews` の個別フェーズ画面を統合ワークスペース画面で置き換える。
2. The system shall 既存の永続データ（生成済みステークホルダー・ペルソナ・取材記録）を統合画面で継続して表示・操作できるようにする。
3. When 既存データが途中フェーズまで存在するトピックを統合画面で開く, the system shall そのトピックの現在の進行状態に対応した操作（次に実行すべき操作）を提示する。
