# Implementation Plan

## 1. 基盤: 型・共通処理・モデル設定

- [x] 1.1 グラウンディング共通処理を `search/grounding.ts` へ抽出
  - 取材エージェント内の出典抽出・URL解決処理（`extractSources` / `resolveSourceUrls`）と出典型（`SearchSource` / `SearchResult`）を共通モジュールへ移す
  - 取材エージェント側の import を直接書き換える（re-export による誤魔化しはしない）
  - 振る舞いは変えない。既存の取材グラウンディングのユニットテストがそのまま通ることを確認できる
  - _Requirements: 3.1, 3.4_
  - _Boundary: search grounding util_

- [x] 1.2 ファクトチェックの永続型を定義する（Functions側）
  - 進捗状態（running / completed / failed）、判定区分（incorrect / unverifiable）、指摘（対象発言・引用・正しい事実・理由・出典）、章単位の結果ドキュメントの型を定義する
  - 指摘は後続の編集工程が機械的に参照できる構造（対象発言と引用、正しい事実、理由、出典）であることを満たす
  - 出典型は 1.1 で共通化した型を利用する
  - 型がビルドを通り、ランナー・リポジトリ・FEから参照できる状態になる
  - _Requirements: 2.3, 3.5, 4.2, 4.3_
  - _Depends: 1.1_

- [x] 1.3 (P) ファクトチェック用のモデル設定を追加する
  - パイプラインモデル設定に2エントリ（grounding 検証用 gemini-2.5-pro、構造化用の軽量 gemini-2.5-flash）を追加し、モデル取得の分岐に加える
  - 両エントリのモデル取得が Gemini プロバイダを返すことを確認できる
  - _Requirements: 3.1_
  - _Boundary: LLM model config_

## 2. コア: バックエンドのファクトチェック実行

- [x] 2.1 (P) ファクトチェック結果の永続化処理を実装する
  - 章配下の結果ドキュメント（章ごとに1件）への書き込み・読み取り・削除を実装する
  - 実行開始時に既存結果を削除してから running を書く、完了で completed、失敗で failed＋エラーメッセージを書く、という進捗状態の遷移を行う
  - 章単位で独立に保存され、章・発言から辿れる形になっている
  - 章を指定すると結果の作成・更新・削除ができることを確認できる
  - _Requirements: 1.3, 1.5, 4.1, 4.3_
  - _Boundary: factCheck repository_
  - _Depends: 1.2_

- [x] 2.2 (P) 発言単位のグラウンディング検証と構造化を実装する
  - 1つの発言を入力に、Phase1（gemini-2.5-pro で Google検索グラウンディング、反証起点に事実主張を検証し出典を解決して番号付きにする）→ Phase2（軽量 gemini-2.5-flash の構造化呼び出しで指摘に整える、grounding なし）を行う
  - 対象発言の id は処理側で固定付与する（LLM出力に依存しない）。引用は当該発言本文の部分文字列であることを照合し、出典は番号参照を解決済み出典に写像する
  - 事実上の誤りが無い主張は指摘を生成しない。出典が得られない主張は「検証不能」とする
  - 1発言を入力に、その発言に対する指摘（誤り／検証不能のみ）の配列が得られることを確認できる
  - _Requirements: 2.2, 2.3, 3.1, 3.2, 3.3, 3.4, 3.6_
  - _Boundary: fact-check runner_
  - _Depends: 1.1, 1.2, 1.3_

- [x] 2.3 章全体のファクトチェックを取りまとめる
  - 章の発言（ペルソナ・ファシリテーター双方）を取得し、検索プロバイダの可用性を確認する。利用不可なら検証せず章全体を検証不能（結果は残す）として終える
  - 各発言を同時実行数を制限して並行に検証し、全発言の指摘を集約する
  - 章を入力に、誤り／検証不能の指摘を集約した結果が得られる（プロバイダ不可時は空＋検証不能注記）ことを確認できる
  - _Requirements: 2.1, 3.6_
  - _Depends: 2.2_

## 3. 統合: 手動実行エンドポイントと再生成連携

- [x] 3.1 ファクトチェック手動実行エンドポイントを実装する
  - 認証必須の onCall として実装し、対象章の存在と完了状態を検証する（未完了は前提条件エラー）
  - 開始時に旧結果を削除して running を書き、章全体の検証を実行し、指摘＋completed を書く。例外時は failed＋エラーメッセージを記録し、討論本体（章・進捗状態）には影響を与えない
  - パイプラインからの自動起動は行わず、本エンドポイント経由でのみ実行される。エクスポートして呼び出せる状態にする
  - 完了章に対し呼び出すと結果ドキュメントが書かれ、未完了章ではエラーになることを確認できる
  - _Requirements: 1.2, 1.5, 4.1, 6.1, 6.3_
  - _Depends: 2.1, 2.3_

- [x] 3.2 (P) 再生成時にファクトチェック結果を無効化する
  - 章の破棄・リセット処理の中で、破棄対象章のファクトチェック結果ドキュメントを削除する
  - 章の発言が再生成されると、その章の既存ファクトチェック結果が消える（自動での再実行はしない）ことを確認できる
  - _Requirements: 6.2_
  - _Boundary: debate chapter lifecycle_
  - _Depends: 2.1_

## 4. フロントエンド: 表示と手動実行ボタン

- [x] 4.1 (P) ファクトチェックのフロント型を定義する

  - _Boundary: FE factCheck model_

- [x] 4.2 (P) ファクトチェック store を実装する

  - 手動実行エンドポイントを呼び出す実行アクションを内包する（討論画面の近傍に置き、中央ディスパッチャは作らない）
  - 結果と実行中・失敗状態が購読でき、実行アクションが呼べることを確認できる
  - _Requirements: 1.2, 5.3, 5.4_
  - _Boundary: factCheck store_
  - _Depends: 4.1, 3.1_

- [x] 4.3 (P) 指摘表示コンポーネントを実装する

  - 指摘を渡すと、誤り箇所・正しい事実・理由・出典が表示されることを確認できる
  - _Requirements: 5.1, 5.2_
  - _Boundary: FactCheckFindings_
  - _Depends: 4.1_

- [x] 4.4 討論管理画面にファクトチェックを組み込む

  - 各発言の直下に、その発言に紐づく指摘を（既存のエンゲージメント等と同列に）表示する
  - 管理画面で完了章のボタンから実行でき、結果が各発言の直下に表示され、実行中はボタンが無効になることを確認できる
  - _Requirements: 1.1, 1.4, 5.1, 5.3, 5.4_
